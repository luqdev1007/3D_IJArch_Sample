# CLAUDE.md

Файл читается агентом в начале каждой сессии. Он описывает **правила игры**, а не задачи.
Задачи и порядок работ — в `PLAN.md`.

---

## 1. Что это за проект

Unity-проект — **vertical slice для портфолио**. Демонстрирует ядро геймплея игры про
пирата-контрабандиста: игрок берёт груз, маскирует его, сдаёт инспектору, инспектор
проверяет груз по правилам из конфига и выносит вердикт.

Проект строится поверх существующего архитектурного шаблона (свой DI-контейнер,
feature-slice структура, MVP-UI, SaveLoad с абстракцией репозитория, конфиги на
ScriptableObject, AI-FSM). Старый геймплейный слой шаблона — top-down arena survivor —
из проекта удаляется, инфраструктура остаётся и переиспользуется.

**Репозиторий будет читать технический директор или тимлид, а не игрок.**
Приоритеты в порядке убывания:

1. Читаемость и последовательность архитектуры
2. Работающая петля от начала до конца
3. Визуал

Мёртвый код, закомментированные блоки, `TODO` без тикета и папки-призраки — недопустимы.
Один закомментированный `Update()` обесценивает весь репозиторий сильнее, чем отсутствие фичи.

## 2. Скоуп заморожен

### Петля слайса — ровно семь шагов

1. Игрок ходит по сцене от первого лица (физический контроллер)
2. Наводится на ящик и берёт его в руки (физический перенос, не парентинг)
3. Ставит ящик на станцию
4. Применяет модификацию: **покраска** и/или **штамп**
5. Несёт ящик к стойке инспектора и сдаёт
6. Инспектор прогоняет груз через список правил из конфига и выносит вердикт
7. Вердикт меняет баланс кошелька и записывается в сейв

### Вне скоупа

Не реализовывать, не предлагать, не «закладывать на будущее»:

- Абордаж, корабли, море, плавание, навигация
- Диалоговые деревья, ветвление реплик, озвучка (инспектор выдаёт готовый текст вердикта)
- Переливание жидкостей и любые модификации, кроме покраски и штампа
- Патрулирование, зрение, слух, NavMesh — инспектор статичен у стойки
- Мультиплеер, сеть, кооп
- Прокачка, магазин, метагейм, прогрессия между сменами
- Реальная интеграция Steamworks SDK (сохраняется только шов `IDataRepository`)
- Продакшн-арт, анимации персонажа, VFX сверх примитивов и простых партиклов

**Если задача выглядит как выход за скоуп — остановись и спроси.** Не расширяй скоуп
самостоятельно, даже если это «десять минут работы».

## 3. Три зоны кода

### 🔒 Ядро — не трогать

Изменения только по явной просьбе, с объяснением причины:

- DI-контейнер и его внутренности (scoped/singleton/non-lazy, детекция циклов)
- Бутстрап-флоу и порядок инициализации
- `SaveLoadService`, `IDataRepository` и сериализатор
- Базовый слой MVP-UI (`IPresenter` / `IView`) и `PopupService`
- `ConfigsProviderService` и механика загрузки конфигов
- Базовые классы FSM (и геймплейной, и AI)

### 🔧 Расширяемое — можно дописывать, нельзя ломать API

- Реализации `IAssetsLoader` (добавляется Addressables-реализация)
- Реализации `IDataRepository`
- Новые состояния для существующих FSM
- Новые контейнеры конфигов
- Новые презентеры и вьюхи поверх существующего MVP

### ✏️ Новое — свободная зона

- Фича-папки нового геймплея (см. глоссарий ниже)
- Editor-инструменты
- Сборщик сцены

## 4. Правила кода

- **Зависимости только через DI-контейнер.** Никаких `FindObjectOfType`,
  `GameObject.Find`, `Resources.FindObjectsOfTypeAll`, статических синглтонов
  и изменяемого статического состояния.
- **Никаких `Resources.Load`** в обход `IAssetsLoader`. Папка `Resources/` — на удаление.
- **Только новый Input System.** `Input.GetAxis`, `Input.GetKey`, `Input.mousePosition`
  и прочий legacy — не использовать. Схема ввода — через `InputActionAsset`.
- **Никаких магических чисел в коде.** Скорости, силы, дистанции, цены, тайминги —
  в ScriptableObject-конфиги.
- **`[SerializeField] private`** вместо публичных полей.
- **Namespace повторяет путь к папке.** Одна папка — одна ответственность.
- **Никакого LINQ и аллокаций в `Update` / `FixedUpdate`.** Кеши и пулы — заранее.
- **Физика — в `FixedUpdate`**, ввод и рейкасты интерфейса — в `Update`.
- **`Debug.Log` не остаётся в коммите.** Допустимы только `LogError`/`LogWarning`
  в ветках реальных ошибок.
- **Комментарии объясняют «почему», а не «что».** Если нужен комментарий «что» —
  переименуй метод.
- **Никаких `#region`.**
- Публичные типы и методы, торчащие наружу фичи, — через интерфейс.
  Внутренности фичи — `internal` или `private`.

### Собственный ECS

В шаблоне есть самописный ECS. **В этом слайсе он не используется для физики и
взаимодействия.** Перенос груза, рейкасты, столкновения — обычные MonoBehaviour +
Unity Physics. Причина: у нас десятки объектов, а не десятки тысяч; прогонять PhysX
через самописный ECS без Burst/Jobs — усложнение без выигрыша.

Если ECS остаётся в репозитории — он должен быть либо реально задействован в
подходящей задаче, либо вынесен в отдельную папку/ассембли с README, объясняющим,
что это инфраструктурный эксперимент. Полумёртвого ECS в проекте быть не должно.

## 5. Работа с Unity через MCP

Это самая частая причина поломок. Соблюдать строго.

- **Никогда не редактировать `.meta` файлы.** Ни создавать, ни менять GUID вручную.
- **Не редактировать `.unity` и `.prefab` как текст.** Сцены и префабы создаются и
  меняются только через Editor-скрипт (`SceneBuilder`) или через MCP-инструменты
  Unity — никогда правкой YAML.
- **Сцена собирается кодом.** Ручная расстановка объектов в редакторе не воспроизводима
  и не читается в ревью. Всё содержимое игровой сцены создаёт детерминированный
  Editor-инструмент.
- **После каждого изменения C# — дождаться перекомпиляции и прочитать консоль.**
  Не переходить к следующему файлу, пока проект не компилируется.
- **Не добавлять и не обновлять пакеты** (`manifest.json`) без явного разрешения.
- **Не менять Project Settings** (Physics, Time, Quality, render pipeline) без
  явного разрешения.
- Не запускать Play Mode без просьбы. Если нужна проверка — предложи, что именно
  проверить, и дождись ответа.
- Не изменять `.gitignore`, `.gitattributes` и настройки Git LFS без разрешения.

## 6. Доменный глоссарий

Единые имена. Не изобретать синонимы, не переименовывать по ходу.

| Термин | Тип | Смысл |
|---|---|---|
| `CargoDefinition` | ScriptableObject | Описание типа груза: id, отображаемое имя, легальность, префаб |
| `CargoInstance` | runtime-класс | Конкретный ящик в мире: ссылка на definition + текущее состояние маскировки |
| `CargoProperty` | enum / данные | Свойство груза, проверяемое инспектором (цвет краски, наличие и валидность печати, вес) |
| `IInteractable` | интерфейс | Объект, на который можно навестись и с которым можно взаимодействовать |
| `InteractionRaycaster` | MonoBehaviour | Луч из камеры, ищет `IInteractable`, отдаёт в UI подсказку |
| `CarryController` | MonoBehaviour | Физический захват и перенос груза |
| `ModificationStation` | абстракция | База для станций модификации |
| `PaintStation` / `StampStation` | MonoBehaviour | Конкретные станции: покраска, штамп |
| `DeliveryCounter` | MonoBehaviour | Стойка сдачи груза инспектору |
| `InspectionRuleConfig` | ScriptableObject | Одно правило проверки: условие + вес нарушения |
| `InspectionService` | сервис | Прогоняет `CargoInstance` через список правил |
| `InspectionResult` | data | Список сработавших правил + итоговый `Verdict` |
| `Verdict` | enum | `Accepted` / `Fined` / `Confiscated` |
| `ContractConfig` | ScriptableObject | Заказ: какой груз, куда, за сколько |

**Ключевая идея, которую нельзя размывать:** проверка инспектора — это data-driven
прогон списка правил над набором свойств груза. Ни одно правило не должно быть зашито
в C#-условиях. Добавление нового правила — это создание нового ScriptableObject-ассета
без изменения кода.

## 7. Definition of Done для слайса

- [ ] Проект компилируется без ошибок и предупреждений в своём коде
- [ ] Игровая сцена собирается одной командой Editor-инструмента
- [ ] Все семь шагов петли проходятся подряд без вылета и без застревания
- [ ] Ни одного `Resources.Load`, ни одного legacy `Input.*`, ни одного `FindObjectOfType`
- [ ] Ассеты грузятся через Addressables-реализацию `IAssetsLoader`
- [ ] Правила инспектора лежат в ассетах; добавление правила не требует правки кода
- [ ] Баланс кошелька сохраняется и восстанавливается между запусками
- [ ] В репозитории нет закомментированного кода и папок survivor-слоя
- [ ] `README.md` объясняет архитектуру, точки расширения и осознанные компромиссы

## 8. Процесс

1. **Сначала план, потом код.** Любая задача крупнее одного файла начинается с
   записи в `PLAN.md`: какие файлы затрагиваются, что в них меняется.
2. **Один этап за проход.** Не начинать следующий этап `PLAN.md`, не получив
   подтверждения, что предыдущий принят.
3. **Коммит на этап.** Формат: `feat:`, `fix:`, `refactor:`, `chore:`.
   Сообщение — по-английски, одна строка, без упоминания AI-ассистента.
4. **Ветка на этап:** `feature/<номер-этапа>-<короткое-имя>`.
5. **Если непонятно — спросить.** Одна уточняющая просьба дешевле, чем день не в ту
   сторону. Не додумывать требования.
6. **Не рефакторить попутно.** Увидел проблему вне текущего этапа — запиши в
   `PLAN.md` в раздел «Замечено по пути», не чини.
